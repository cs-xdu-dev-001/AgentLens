# KnowFlow AI前端深度精修设计方案

## 1. 目标与边界

本轮不是重做前端，而是在当前可用界面上完成一次系统性精修。保留现有黑白中性色、左侧导航、中部对话、右侧运行面板、页面入口和主要交互；不改名、不换Logo、不重排导航，不删除Agent过程可视化。

完成后应达到三个结果：

1. 字号、字重、行高、间距、圆角、边框和控件状态形成统一体系。
2. 设置、运行面板、知识库、Skills、记忆和MCP页面看起来属于同一产品。
3. 桌面端更适合长时间工作，移动端核心任务可连续完成。

本轮不重构后端业务，不新增未经验证的能力，不渲染隐藏思维链、Secret、Token或未经脱敏的内部日志。

## 2. 现状判断

当前界面的信息架构和视觉方向是成立的，主要问题来自样式长期叠加：

- `frontend/styles.css`存在多轮样式覆盖，同类组件出现多个字号、圆角和间距。
- 页面各自形成局部语法，设置页、管理页和运行面板的密度不一致。
- 部分界面依赖“大标题＋辅助小字”或重卡片表达层级，核心信息不够直接。
- 运行面板保留了过程，但节点详情、日志摘要、错误恢复和可操作性仍不统一。
- 桌面端基本可用，窄屏、长文本、空状态、错误状态和键盘体验缺少统一验收。

因此采用“收敛式优化”，而不是新增另一层覆盖样式或更换视觉世界。

## 3. 设计方向

设计北极星为“安静的可见工作台”。主内容区保持专注，运行面板解释Agent正在做什么；视觉通过排版、间距、边界和真实状态建立专业感，不依赖渐变、玻璃、发光、厚阴影或装饰卡片。

规范来源为根目录`DESIGN.md`，扩展元数据和组件示例位于`.impeccable/design.json`。实现期间若发现规范与现有功能冲突，以不破坏功能和用户确认过的现状为先，并更新规范而不是私自改结构。

## 4. 实施分层

### 4.1 基础层

- 建立单一规范层，集中定义颜色、文字角色、间距、圆角、边框、阴影、焦点和动效。
- 逐步删除被最终规范完全覆盖的旧规则，避免继续在文件末尾追加补丁。
- 保持现有React组件边界，只有在同一视觉模式重复三次以上时才抽取共享组件。
- 所有交互控件补齐`hover`、`focus-visible`、`active`、`disabled`和错误状态。

### 4.2 聊天与输入框

- 保留现有对话布局和融合悬浮输入框。
- 收敛输入框两层结构，让文本区、模型选择、Skill入口、附件和发送动作属于一个整体。
- 模型切换保持就地完成，不新增占据正文空间的配置面板。
- 回答正文优化中英文混排、表格、代码块、列表、引用和超长链接。

### 4.3 右侧运行面板

- 第一层展示运行状态、当前进度、总耗时、工具调用数和节点时间线。
- 节点一眼可读：类型、任务名称、状态、耗时；选中后再展开公开输入、结果摘要、来源、错误和恢复动作。
- 日志信息只渲染经后端分类和脱敏的数据，不输出原始服务日志或隐藏思维链。
- 对等待、运行、成功、失败、跳过、需要审批和后台处理中建立统一状态文本与图形语言。
- 进度必须与后端持久化状态收敛，结束态不可停留在等待或运行。

### 4.4 设置页

- 保留模型配置列表—详情/编辑结构。
- 列表项只展示名称、提供商、模型、协议和可用状态；密钥仅显示是否配置。
- 表单默认只保留必要字段：配置名、协议、模型名、接口地址、API密钥和最大输出；温度、Top P等非必要参数移入高级设置或移除。
- 已保存配置使用紧凑列表，不使用大卡片堆叠；编辑、设为默认、复制、删除进入清晰的行级操作。
- 保存前执行协议级连接测试，错误说明失败端点、状态类别和下一步，不暴露密钥。

### 4.5 知识库、Skills、记忆与MCP

- 四类管理页面统一使用标题工具栏、紧凑列表、详情区和明确空状态。
- 知识库突出文档状态、解析进度和失败恢复。
- Skills突出名称、作用、来源、启用状态和依赖，不重复展示冗长说明。
- 记忆突出已启用状态、记忆正文、来源时间和编辑/删除，不把实现参数放在主视图。
- MCP突出连接状态、鉴权方式、暴露工具数和风险动作；OAuth和错误恢复保持可操作。

### 4.6 响应式与无障碍

- 1180px以下允许运行面板覆盖或收窄；900px以下左侧导航进入抽屉；720px以下切换单列。
- 移动端仍可发送消息、切换模型、选择Skill、处理审批、查看运行进度和错误。
- 所有图标按钮提供可访问名称；焦点顺序与视觉顺序一致；弹窗和抽屉支持Escape关闭并正确恢复焦点。
- 正文和关键控件达到WCAG AA对比度，状态不能只靠颜色区分。

## 5. 实现策略

### 5.1 不新增长期样式债

先为目标页面建立静态契约测试，再修改样式。实现按“基础层→聊天与运行面板→设置页→管理页面→响应式”的顺序进行。每一阶段优先重用现有类名和组件，只有确认旧规则无调用后才删除。

### 5.2 数据与接口

前端只消费现有公开数据。若运行面板确实缺少必要信息，先定义脱敏字段和向后兼容的事件结构，再做最小后端补充；禁止把journal、异常堆栈、请求头或完整工具输出直接传给前端。

### 5.3 状态处理

每个异步页面至少覆盖：加载、空、成功、部分成功、失败、重试和无权限。聊天运行还需覆盖等待审批、用户取消、后台记忆写入和会话切换。

## 6. 验证方案

1. 为视觉契约和关键状态新增或更新`tests/check_*.py`，实现前先看到针对旧行为的失败。
2. 运行全部`tests/check_*.py`，不得跳过或只跑新增测试。
3. 运行`frontend npm run build`和`git diff --check`。
4. 对实际改动目标运行一次`impeccable`手动检测器，处理真实问题，避免为检测器分数重构。
5. 在桌面宽屏、1180px、900px和720px以下进行截图验收，覆盖聊天、运行面板、设置、知识库、Skills、记忆和MCP。
6. 验证键盘导航、长文本、空状态、错误状态、暗色主题和模型/Skill切换。
7. 最多进行两轮视觉回归修正，达到规范即收尾，避免无止境微调。

## 7. 交付与安全

- 不提交`.env`、数据库、上传文件、`frontend/dist`、`data/mem0`、Key、Token或浏览器配置。
- 不使用`git reset`、`git clean`或回滚现有修改。
- 实现完成后检查全部diff、测试、构建和敏感信息，再提交并推送`origin/main`。
- 推送后提供服务器Codex可直接粘贴的同步与部署提示词。

## 8. 验收标准

- 用户一眼仍能认出当前KnowFlow AI，而不是一套新产品。
- 常用页面使用同一套文字、间距、圆角、边框和状态语法。
- 核心信息不依赖低对比小字；页面不再堆叠大标题和说明卡片。
- Agent过程更易读、更可操作，同时不泄露敏感信息或思维链。
- 桌面端无明显错位，移动端可完成核心任务。
- 全量检查、前端构建、diff检查和发布卫生全部通过。
