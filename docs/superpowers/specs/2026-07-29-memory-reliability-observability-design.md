# Mem0记忆可靠性与可观测性设计

日期：2026-07-29
状态：已确认
范围：KnowFlow AI普通聊天、Agent运行轨迹、长期记忆管理

## 1. 背景

KnowFlow AI已经完成Mem0 2.0.14接入，具备按用户启用、召回、异步写入、列表、编辑、删除和清空能力。生产环境已验证中文记忆写入、Qdrant持久化和跨请求读取。

当前缺口不在“能否记住”，而在“能否可靠、透明地记住”：

- 普通聊天与Agent在回答保存后异步调用`remember_async()`，调用方丢弃`Future`。
- 写入异常只进入日志，前端不知道任务是否成功。
- 服务重启后无法恢复尚未执行的写入。
- 上游超时、限流和5xx没有自动重试。
- 模型可能在写入完成前使用“已牢记”等无法验证的表述。
- 召回和写入没有出现在Agent运行轨迹中。

## 2. 目标

1. 记忆故障仍然不能阻断正常回答。
2. 记忆写入具备持久任务、有限重试、重启恢复和幂等保护。
3. 用户能在回答下方看到紧凑状态，并按需查看本轮引用和变更。
4. Agent运行轨迹能显示`MEMORY`召回、写入节点及实时状态。
5. 所有查询、详情和重试继续保持严格用户隔离。
6. 模型不得在写入完成前自行宣称“已记住”。

## 3. 非目标

- 不引入Celery、Redis、Kafka等外部任务系统。
- 不改变Mem0作为长期记忆引擎的定位。
- 不新增独立的常驻记忆抽屉或第三套运行界面。
- 不展示模型内部推理、原始提示词或上游原始响应。
- 不在本轮实现记忆优先级、自动衰减、版本恢复或跨用户共享。

## 4. 产品基准与设计原则

ChatGPT将长期记忆作为独立、可查看和可删除的用户数据，并允许用户了解回答引用了哪些个性化来源。KnowFlow采用相同的“用户可控”原则，但不复制其产品结构。[OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq)

KnowFlow现有Agent运行抽屉已经承载模型、工具、MCP和Skill步骤。本设计把记忆作为一种新的运行步骤接入，不新增常驻卡片。

视觉原则：

- 消息下方只出现一行状态。
- 无召回、无变更且无错误时不显示。
- 点击状态行后复用现有“本次运行”抽屉。
- 成功使用青绿色，处理中使用蓝色脉冲，失败使用红色。
- 详情默认收起，不让小字号承担核心结果。

## 5. 方案选择

### 方案A：仅写入`trace_json`

优点是改动小。缺点是普通聊天与Agent的数据结构不统一，异步完成后回写困难，服务重启后不能恢复任务。

### 方案B：持久任务加运行轨迹投影

新增单一`memory_operation`实体负责状态、重试和结果；聊天状态行与Agent轨迹均由该实体投影。可靠性与可观测性统一，且不需要外部队列。

### 方案C：同步完成写入后再返回回答

状态最准确，但每个回答增加一次LLM、Embedding和向量库延迟，上游抖动会直接影响聊天体验。

采用方案B。

## 6. 数据模型

新增`memory_operation`表：

| 字段 | 用途 |
|---|---|
| `id` | 操作ID，随机不可预测 |
| `user_id` | 所属用户 |
| `session_id` | 所属会话 |
| `message_id` | 对应assistant消息，召回阶段可先为空后回填 |
| `agent_run_id` | 对应Agent运行，可为空 |
| `kind` | `recall`或`write` |
| `status` | `queued`、`running`、`succeeded`、`failed` |
| `attempt_count` | 已执行次数 |
| `next_attempt_at` | 下一次可执行时间 |
| `result_json` | 记忆ID、动作与用户可见摘要 |
| `error_code` | 脱敏错误类别 |
| `error_message` | 可展示的安全错误摘要 |
| `started_at` | 最近一次开始时间 |
| `finished_at` | 最终完成时间 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

约束：

- 唯一键：`(user_id, message_id, kind)`。
- 所有读取和更新必须同时带`user_id`。
- 不在任务表复制完整聊天内容。重试时按用户、会话和消息读取原消息。
- `result_json`只保存本轮使用或变更的记忆ID、动作、短摘要，不保存模型原始响应。
- 用户删除单条记忆时清除关联摘要；清空全部记忆时清除该用户所有任务摘要。
- 运行记录保留30天，清理仅删除任务审计数据，不删除长期记忆。

## 7. 状态机与执行规则

```text
queued -> running -> succeeded
                  -> queued    可重试错误且次数未用尽
                  -> failed    永久错误或次数耗尽
```

执行流程：

1. 请求进入后创建或更新`recall`操作。
2. 召回成功记录引用结果；召回失败记录安全错误，但向模型传入空记忆并继续回答。
3. assistant消息保存成功后，将召回操作关联到`message_id`并创建`write`操作。
4. 后台执行器领取到期任务，将状态原子更新为`running`。
5. 首次失败后5秒重试，第二次失败后30秒重试，最多执行3次。
6. 仅超时、连接错误、429和上游5xx进入重试；400、401、403、模型不兼容和本地配置错误直接失败。
7. 服务启动时把超时的`running`恢复为`queued`，并领取所有到期任务。
8. 服务关闭时停止领取新任务，等待当前调用结束；未执行任务保留在数据库。

幂等策略：

- 每个写入任务生成稳定`operation_id`，写入Mem0 metadata。
- 调度层唯一键避免同一消息重复创建任务。
- 重试前按`operation_id`核对是否已经产生结果；已存在则直接标记成功。
- 如果Mem0版本或过滤能力无法可靠核对，模糊网络故障不盲目重复写入，而是标记为可手动重试，避免制造重复记忆。

## 8. 后端结构

新增职责：

- `MemoryOperationStore`：任务创建、按用户查询、原子领取、状态更新、重启恢复、过期清理。
- `MemoryOperationRunner`：错误分类、重试调度、调用`MemoryManager`并保存结果。
- `MemoryActivityProjector`：把操作记录转换为前端统一活动结构和Agent trace step。

保留职责：

- `Mem0MemoryProvider`继续封装Mem0 API。
- `MemoryManager`继续处理用户开关、召回和记忆CRUD。
- 普通chat和Agent路由只负责创建任务、关联消息，不直接维护重试逻辑。

不新增独立进程。当前单worker部署中，由应用内后台执行器消费持久任务。

## 9. API

### 获取消息记忆活动

`GET /api/messages/{message_id}/memory-activity`

返回：

```json
{
  "messageId": 42,
  "summary": {
    "recalled": 2,
    "added": 1,
    "updated": 0,
    "deleted": 0
  },
  "operations": [
    {
      "id": "memop_xxx",
      "kind": "write",
      "status": "succeeded",
      "attemptCount": 1,
      "items": []
    }
  ]
}
```

### 手动重试

`POST /api/memory/operations/{operation_id}/retry`

规则：

- 仅操作所属用户可调用。
- 仅`failed`状态可重试。
- 新一轮仍执行自动重试规则。
- 已成功任务返回冲突，不重复写入。

### 消息列表

现有消息返回可附带轻量`memoryActivity`摘要，避免首次渲染为每条消息单独请求。详细内容仍按需获取。

## 10. Agent运行轨迹

Agent执行时新增两个`kind: "memory"`步骤：

1. `记忆召回`：位于第一次模型调用前。
2. `记忆写入`：位于回答保存后。

运行中继续发送现有`agent_step`事件，前端`mergeTraceStep()`按`stepId`合并。写入在流结束后仍可能继续，Agent运行查询接口必须从`memory_operation`投影最新状态，不能只依赖流结束时的静态`trace_json`。

步骤详情只显示：

- 实际引用的记忆。
- 新增、更新、删除的记忆。
- 尝试次数。
- 脱敏失败类别。
- “重试”和“前往记忆页”操作。

## 11. 普通聊天交互

消息状态文案：

- 处理中：`参考了2条记忆 · 正在整理记忆…`
- 成功：`参考了2条记忆 · 新增1条`
- 失败：`记忆写入失败 · 重试`
- 无引用、无变更且无错误：不显示

点击状态行打开现有“本次运行”抽屉并选中对应`MEMORY`节点。普通聊天在回答完成后进行短时轮询，任务进入终态或页面离开时停止。

模型系统提示增加硬约束：

- 写入状态未知时，不得宣称“已牢记”“已经存入长期记忆”。
- 可以说“我会尝试记录，结果会显示在回答下方”。
- UI状态是记忆写入成功与否的唯一权威结果。

## 12. 安全与隐私

- 所有任务接口执行用户归属校验。
- 操作ID随机且不可枚举。
- 日志只记录`operation_id、kind、status、attempt_count、error_code`。
- 不记录聊天原文、记忆文本、API Key、模型原始响应或内部推理。
- API错误只返回稳定错误码和安全文案。
- 用户清空记忆时同步清除任务结果摘要。
- 任务查询限量并按时间倒序，防止无界读取。

## 13. 测试

后端新增检查：

- 普通chat和Agent的召回、消息保存、任务创建时序。
- 召回失败不阻塞回答。
- 写入成功、可重试失败、永久失败状态。
- 最多3次执行与5秒、30秒退避。
- 服务重启恢复`queued`和过期`running`。
- 唯一键和`operation_id`防重复。
- 不同用户不能读取或重试他人操作。
- 删除和清空记忆会清除任务摘要。
- 日志和API不泄露Key、原始上游响应或聊天原文。
- 关闭流程不会在后台仍访问provider时提前关闭客户端。

前端新增检查：

- 无活动时不显示状态行。
- running、success、failed文案与颜色正确。
- 点击状态行打开现有抽屉并选中`MEMORY`节点。
- 手动重试后状态更新。
- 375px宽度下状态行和底部抽屉不横向溢出。

发布门禁：

- 全部`tests/check_*.py`
- `frontend npm run build`
- `git diff --check`
- `.env`、数据库、上传文件、`frontend/dist`、Key和Token排除检查

生产验收：

1. 新会话引用旧会话形成的长期记忆。
2. 用户纠正旧偏好后，后续会话只使用新值。
3. 模拟上游临时故障后自动重试成功。
4. 模拟永久故障后显示“未记住·重试”。
5. 服务重启后待执行任务继续完成。
6. 两个用户的记忆和操作记录完全隔离。
